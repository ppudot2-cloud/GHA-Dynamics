Before You Start — Prerequisites

Make sure you have these before touching anything below
  • You are a Global Administrator or Application Administrator in Azure Active Directory
  • You are a Power Platform Administrator or System Administrator in each Dynamics 365 environment
  • You have a JFrog Artifactory instance (cloud or on-premise) — or a JFrog Cloud free account at jfrog.com
  • You have Admin access to the GitHub organisation and both repositories (GHA-Dynamics and GHA-Core)
  • All 6 Power Platform environments exist and are running: Sandbox, Dev, Intg, UAT, Perf, Prod
  • You know each environment's URL — how to find it →
ℹ️ One App Registration, All Environments
You only create ONE Azure App Registration. The same App ID and Client Secret is used across all Power Platform environments. You just need to register it as an Application User inside each environment separately (Section 2).

Azure App Registration (Service Principal)

This is the "identity" your CI/CD pipeline uses to talk to Power Platform. Think of it as creating a dedicated service account.

Create the App Registration

Open the Azure Portal

Go to portal.azure.com and sign in with your admin account.

Navigate to App Registrations
Azure Active Directory → App registrations → + New registration
Fill in the registration form

Use the values below exactly:

FieldValue to enter
NamePowerPlatform-CI-CD (or any name you prefer)
Supported account types✅ Accounts in this organizational directory only (Single tenant)
Redirect URILeave blank — not needed

Click Register.

You're on the app's Overview page — save these two values now
🔵Application (client) IDxxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx ← this is your APP_ID
🟣Directory (tenant) IDxxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx ← this is your TENANT_ID
⚠️ Copy these now — you'll need them in Section 4
Open a Notepad/Notes app and paste both values. Label them clearly.

Add API Permissions for Dynamics CRM

Open API permissions
API permissions → + Add a permission
Find Dynamics CRM

In the panel that opens, click "APIs my organization uses" tab, then search for Dynamics CRM. Click on it when it appears.

Select the permission

Choose Delegated permissions, tick user_impersonation, then click Add permissions.

Grant admin consent

Back on the API permissions page, click "Grant admin consent for [Your Org]". A confirmation dialog appears — click Yes.

✅ The status icon next to user_impersonation should turn green.

If the "Grant admin consent" button is greyed out, you don't have the right permissions. Ask your Azure Global Administrator to do this step.

Power Platform — Register Application User

Tell each Power Platform environment "trust this Azure app". You must do this in every single environment your pipeline will touch.
ℹ️ Why is this needed?
Azure only gives your app an identity — it doesn't automatically give it access to your Dataverse environments. You have to explicitly add it as an "Application User" inside each environment and grant it the System Administrator role so it can import solutions, run Solution Checker, etc.

Add the Application User (do this once per environment)

Open Power Platform Admin Center

Go to admin.powerplatform.microsoft.com and sign in.

Select your environment
Environments → click your environment name → Settings
Navigate to Application users
Users + permissions → Application users → + New app user
Add your App Registration

Click "+ Add an app". A search box appears. Type the name you gave your app registration (PowerPlatform-CI-CD) or paste the App ID. Select it and click Add.

Assign the Security Role

Under Security roles, click the edit (pencil) icon. Tick System Administrator. Click Save.

⚠️ Must be System Administrator — not just System Customizer
The pipeline needs to backup environments, import solutions, and run Solution Checker. "System Customizer" is not enough — it will cause permission errors during deployment.
Click "Create"

The Application User is now listed with a blue robot icon in the user list.

Repeat for Every Environment

Go back to step 2 above and repeat the entire process for each environment in the table below. The APP_ID is the same every time — only the environment changes.

GitHub — Secrets & Variables

Store all credentials and configuration in GitHub so your workflows can access them securely. You must configure these in BOTH the GHA-Dynamics and GHA-Core repositories.
ℹ️ Secrets vs Variables — what's the difference?
Secrets are encrypted passwords/keys — GitHub hides them in logs. Variables are plain text config values like URLs — visible in logs. Never put passwords in Variables. Never put URLs in Secrets.

Step 1 — Create the GHA_CORE_PAT (do this first)

This is a GitHub Personal Access Token that allows GHA-Dynamics to check out code from the private GHA-Core repository during pipeline runs.

Open your GitHub profile settings
Profile photo (top right) → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token
Configure the token
FieldValue
Token nameGHA-Core-CI-Access
Expiration1 year (set a calendar reminder)
Resource ownerYour GitHub Organisation
Repository accessOnly selected repositories → choose GHA-Core

Under Repository permissions, set:

ContentsRead-only
WorkflowsRead-only

Click Generate token and copy the token value now.

Step 2 — Add Repository Secrets to GHA-Dynamics

GHA-Dynamics repo → Settings → Secrets and variables → Actions → Secrets tab → New repository secret

Add each of these secrets one by one — click "New repository secret", enter the Name and Secret, click Add:

Secret NameValue to pasteWhere it came from
APP_ID Your Azure App Registration's Application (client) ID Section 1 — Azure Overview page REQUIRED
CLIENT_SECRET The secret value you copied from Azure Section 1 — Certificates & secrets REQUIRED
TENANT_ID Your Azure Directory (tenant) ID Section 1 — Azure Overview page REQUIRED
JFROG_API_KEY Your JFrog API key / Identity Token Section 3 — JFrog profile REQUIRED
GHA_CORE_PAT The GitHub Personal Access Token you just created Step 1 above REQUIRED
💡 Add the same secrets to GHA-Core too
Navigate to the GHA-Core repo → Settings → Secrets → and add APP_ID, CLIENT_SECRET, TENANT_ID, JFROG_API_KEY with the same values. GHA_CORE_PAT is not needed in GHA-Core.

Step 3 — Add Repository Variables to GHA-Dynamics

GHA-Dynamics repo → Settings → Secrets and variables → Actions → Variables tab → New repository variable

Add each variable below. Replace the example values with your actual environment URLs:

Variable NameExample ValueDescription
PP_SDBX_URL https://yourorg-sdbx.crm4.dynamics.com Sandbox environment — used for Solution Checker auth and config export REQUIRED
PP_DEV_URL https://yourorg-dev.crm4.dynamics.com Dev environment URL REQUIRED
PP_INTG_URL https://yourorg-intg.crm4.dynamics.com Integration environment URL REQUIRED
PP_UAT_URL https://yourorg-uat.crm4.dynamics.com UAT environment URL REQUIRED
PP_PERF_URL https://yourorg-perf.crm4.dynamics.com Performance environment URL REQUIRED
PP_PROD_URL https://yourorg-prod.crm4.dynamics.com Production environment URL REQUIRED
JFROG_URL https://yourcompany.jfrog.io/artifactory JFrog Artifactory base URL — no trailing slash REQUIRED
JFROG_REPO powerplatform-solutions Name of the JFrog repository you created REQUIRED
PP_CHECKER_GEO UnitedStates or Europe Geography for Solution Checker API endpoint. Use the region closest to your tenant. REQUIRED
PP_SOLUTION_NAME CoreSolution Only needed for single-solution repos. Leave blank for multi-solution repos. OPTIONAL
PP_DATA_SCHEMA_FILE config/schema.xml Path to Configuration Migration data schema. Leave blank if not using config data export. OPTIONAL
ℹ️ Which crm number do I use in the URL?
The number after crm depends on your Azure region. Common ones:
  • crm — North America
  • crm4 — EMEA (Europe, Middle East, Africa)
  • crm5 — Asia Pacific
  • crm6 — Australia
  • crm7 — Japan
  • crm8 — India
  • crm11 — United Kingdom
The easiest way: copy the URL directly from Power Platform Admin Center — it already has the correct number.

GitHub Environments & Deployment Gates

Environments are GitHub's "approval gates". When the pipeline reaches a gate, it pauses and waits for a human to click Approve before deploying to that environment.
ℹ️ How gates work in your pipeline
After the build succeeds, all four non-prod gates (Dev, Intg, UAT, Perf) become available simultaneously. A reviewer can approve any one of them — those environments deploy in parallel while unapproved ones wait. Prod only opens after UAT has successfully deployed.

Create Each Environment

GHA-Dynamics repo → Settings → Environments → New environment

Create six environments — the names must match exactly as shown (case-sensitive):

Environment NameTypeApproval needed?
DevUnmanaged solution deployOptional — your choice
IntgManaged solution deployRecommended
UATManaged solution deployRecommended
PerfManaged solution deployRecommended
ProdManaged solution deployMandatory — always

Configure Protection Rules (repeat for each environment)

Click on the environment name

From Settings → Environments, click the environment you just created.

Enable "Required reviewers"

Tick the Required reviewers checkbox. A search box appears. Search for and add the people or teams who should approve deployments to this environment.

💡 Tip — use Teams, not individuals
Add a GitHub Team (e.g. "platform-approvers") rather than individual users. This way, if someone leaves the team, approvals keep working automatically.
Set a "Wait timer" (optional but recommended for Prod)

For the Prod environment, set a wait timer of 5 minutes. This gives people a short window to cancel an accidental approval before the deployment actually starts.

Restrict deployment branches (highly recommended for Prod)

Under Deployment branches, change "All branches" to Selected branches and add main. This means only code merged into main can deploy to Prod — no accidental deployments from feature branches.

Click "Save protection rules"

Repository Structure & Deployment Settings

Your solution repo (GHA-Dynamics) must follow this folder structure for the pipeline to find everything automatically.

Required Folder Layout

GHA-Dynamics/ ├── src/ │ └── solutions/ │ └── YourSolutionName/ # ← exact name must match PP solution name │ ├── Other/ │ │ └── Solution.xml # ← pipeline reads version from here │ ├── Entities/ │ ├── Workflows/ │ └── ... # other unpacked solution files │ ├── deployment-settings/ │ ├── dev/ │ │ └── YourSolutionName.json # connection references for Dev │ ├── intg/ │ │ └── YourSolutionName.json │ ├── uat/ │ │ └── YourSolutionName.json │ ├── perf/ │ │ └── YourSolutionName.json │ └── prod/ │ └── YourSolutionName.json │ └── config/ └── YourSolutionName/ └── config-data.zip # config migration data (optional)

Deployment Settings Files

Each YourSolutionName.json file tells Power Platform which connection references to use in that specific environment. Here's the minimum structure:

// deployment-settings/dev/YourSolutionName.json { "EnvironmentVariables": [ { "SchemaName": "your_variable_schema_name", "Value": "dev-specific-value" } ], "ConnectionReferences": [ { "LogicalName": "your_connection_reference_name", "ConnectionId": "xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx", "ConnectorId": "/providers/Microsoft.PowerApps/apis/shared_sharepointonline" } ] }
💡 How to get connection reference values
After manually deploying to each environment once, run: pac solution export --name YourSolutionName --path . --managed false then inspect the exported deployment-settings.json file — it contains the pre-filled connection reference IDs for that environment.

Troubleshooting — Common Errors

If something fails, check here first
Error MessageCauseFix
APP_ID secret is not set The secret wasn't added to the repo, or there's a typo in the secret name Go to Settings → Secrets → confirm APP_ID exists (exact case)
jfrog_url is required JFROG_URL variable is missing or empty Add JFROG_URL as a Repository Variable (not secret)
Unauthorized (401) from JFrog API key is wrong or expired Regenerate the JFrog API key, update the JFROG_API_KEY secret
Not found (404) from JFrog Repository name in JFROG_REPO doesn't exist in JFrog Confirm the repo name in JFrog matches JFROG_REPO variable exactly
Authentication failed / Could not connect to Dataverse App Registration not added as Application User in that PP environment, or wrong APP_ID/CLIENT_SECRET/TENANT_ID Re-check Section 2 — verify the app user has System Administrator role in that environment
Resource not found when checking out GHA-Core GHA_CORE_PAT secret is missing, expired, or the token doesn't have access to GHA-Core repo Regenerate the PAT, ensure it targets the GHA-Core repo with Contents: Read-only
Environment gate never appears / pipeline skips gate GitHub Environment name doesn't exactly match what's in the workflow YAML Compare the name in release-pipeline.yml (e.g. environment: Dev) with the environment name in Settings → Environments. They must match exactly — including capitalisation.
Solution.xml not found Solution source folder structure is wrong Confirm the folder is at src/solutions/YourSolutionName/Other/Solution.xml
