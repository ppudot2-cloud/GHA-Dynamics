Combined Export + Build + Deploy Pipeline

A single workflow_dispatch call drives the full Power Platform release lifecycle — exporting solutions from sandbox, packing and validating artifacts, then promoting through every environment sequentially with approval gates at each stage.

📋 Summary
Always runs
Gate mechanism: Gates are not separate jobs. Each deploy iteration uses environment: ${{ matrix.env.name }}. GitHub's Environment protection rules pause execution and wait for required reviewers before the runner is provisioned. No extra gate job is needed.
Sequential guarantee: The deploy chain uses max-parallel: 1 on a strategy.matrix. This ensures Dev fully completes before Intg gate fires, Intg before UAT, etc. Dataverse cannot handle parallel solution imports.
⚙️

Setup Job

Runs first, always. Resolves which solutions to build and constructs the environment config matrix. All downstream stages receive its outputs.

Runs Always
🔍 setup combined-pipeline.yml → jobs.setup
1
Checkout repository
actions/checkout@v4
Checks out the GHA-Dynamics repository (the caller) into the runner workspace. Needed so the next steps can read solutions.json and deployment-settings/ files.
2
Checkout GHA-Core CI scripts
actions/checkout@v4 → path: .ci
Checks out the GHA-Core repository into .ci/ inside the workspace. This makes all shared PowerShell scripts (e.g. Resolve-SolutionMatrix.ps1, Write-PipelineSummary.ps1) available to every step that follows. Uses secrets.GHA_CORE_PAT to authenticate against the private GHA-Core repo.

1

Stage 1 — Export

Exports live solutions from the Power Platform sandbox, unpacks them, and uploads the unpacked source as GitHub artifacts for Stage 2 to consume. Runs in parallel across all solutions.

Parallel Optional
Skip conditions: This stage is skipped entirely when skip_export = true OR mock_deploy = true. In that case, Stage 2 builds from the committed src/solutions/ tree instead.
📤 export (one runner per solution, parallel) _stage-export.yml → jobs.export
Fan-out pattern: Uses strategy.matrix: solution: ${{ fromJson(inputs.matrix) }} with fail-fast: false. Each solution gets its own runner. Failures are isolated per solution.
1
CI Bootstrap
ppudot2-cloud/GHA-Core/templates/steps/dynamics/ci-bootstrap@main
Runs on every job in the pipeline as the mandatory first step. Performs: (a) checkout of GHA-Dynamics repo, (b) checkout of GHA-Core into .ci/ using GHA_CORE_PAT, (c) Azure OIDC login (skipped when mock_deploy=true), (d) fetch secrets from Azure Key Vault (PP_APP_ID, PP_CLIENT_SECRET, PP_TENANT_ID, optionally JFROG_TOKEN), (e) merge global and project-level variable files into GITHUB_ENV so all subsequent steps can read them as environment variables.
2
Install PAC CLI
ppudot2-cloud/GHA-Core/templates/steps/dynamics/pac-install@main
Installs the Power Platform CLI (pac) via microsoft/powerplatform-actions/actions-install@v1 and adds it to PATH. Must run before any step that calls pac.
3
Export Solution
ppudot2-cloud/GHA-Core/templates/steps/dynamics/export-solution@main
Authenticates PAC CLI against PP_SDBX_URL (the sandbox) using the service principal credentials fetched in step 1. Exports the unmanaged solution ZIP via microsoft/powerplatform-actions/export-solution@v1, then immediately unpacks it to export-src/<SolutionName>/ using microsoft/powerplatform-actions/unpack-solution@v1. The output source_folder is set to export-src so the upload step knows where to find the files.
Output
source_folderPath to the unpacked source root (export-src). Consumed by the upload step.
4
Upload exported source artifact
actions/upload-artifact@v4
Uploads the unpacked solution source tree as a GitHub Actions artifact named exported-source-<SolutionName>. Retention is set to 1 day (only needed within this run). If no files are found the step fails, which prevents a corrupt artifact from silently reaching Stage 2. Stage 2 (_job-build) downloads this artifact when use_exported_source=true.
2

Stage 2 — Build

Packs unmanaged and managed solution ZIPs, runs Solution Checker, exports config data if needed, and uploads artifacts to JFrog Artifactory. Runs in parallel across all solutions.

Parallel
Always runs — even if Stage 1 was skipped. When stage-export result is skipped, the build packs from the committed src/solutions/ tree. When it is success, the build downloads the exported source artifact from Stage 1 instead.
🏗️ build (one runner per solution, parallel) _stage-build.yml → _job-build.yml → jobs.build
Two-level fan-out: _stage-build.yml uses strategy.matrix + job-level uses: _job-build.yml. This is the only valid GitHub pattern for calling reusable workflows in a parallel matrix (a job with uses: cannot have steps:).
1
CI Bootstrap
ppudot2-cloud/GHA-Core/templates/steps/dynamics/ci-bootstrap@main
Same as Stage 1 Step 1. Checkout, Azure OIDC, AKV secrets, variable merge. jfrog_enabled=true when jfrog_url is set, which causes CI Bootstrap to also fetch JFROG_TOKEN from AKV.
2
Install PAC CLI
ppudot2-cloud/GHA-Core/templates/steps/dynamics/pac-install@main
Installs PAC CLI. Required for solution packing and Solution Checker.
3
Download exported source artifact
actions/download-artifact@v4
if: inputs.use_exported_source == true
When Stage 1 ran successfully, downloads the exported-source-<SolutionName> artifact uploaded in Stage 1 Step 4, placing it at export-src/<SolutionName>/. Skipped entirely when use_exported_source=false (Stage 1 was skipped or mock_deploy=true).
4
Resolve source folder
shell: bash — inline
Decides which source folder to pack from. If use_exported_source=true → sets folder=export-src (the downloaded export). Otherwise → sets folder=src/solutions (or the value of solution_source_folder from the matrix). The output is consumed by the next step.
Output
folderEffective source path for packing.
5
Pack Solution
ppudot2-cloud/GHA-Core/templates/steps/dynamics/pack-solution@main
Reads the version from Solution.xml, computes the artifact name as <SolutionName>_<run_number>_<run_attempt>, strips the <Managed> tag via Remove-ManagedTag.ps1, then calls pac solution pack twice: once for unmanaged (Unmanaged) and once for managed (Managed) ZIPs. Both ZIPs are placed under out/<artifact_name>/.
Outputs
versionVersion string from Solution.xml (e.g. 1.0.20240101.1)
artifact_nameFull artifact ID e.g. CoreSolution_42_1
unmanaged_zipPath to the unmanaged ZIP
managed_zipPath to the managed ZIP
checker_artifact_nameArtifact name for SARIF report
6
Solution Checker
ppudot2-cloud/GHA-Core/templates/steps/dynamics/solution-checker@main
Always mandatory in non-mock builds — there is no way to skip it. Calls microsoft/powerplatform-actions/check-solution@v1 with the unmanaged ZIP and authenticates against the Power Platform tenant using the service principal. The check runs in the geography specified by checker_geo (default: UnitedStates, overridable per solution in solutions.json). Failure threshold is set by checker_error_level. The SARIF results are uploaded as a GitHub artifact named <artifact_name>-checker. In mock mode, a simulated SARIF is produced instead.
7
Export Config Data
ppudot2-cloud/GHA-Core/templates/steps/dynamics/export-config-data@main
if: inputs.data_schema_file != ''
Only runs when data_schema_file is provided in the solution's solutions.json entry. Exports configuration migration data from the sandbox environment using microsoft/powerplatform-actions/export-data@v1 with the given XML schema. The resulting ZIP is packed as a GitHub artifact named config-data-<SolutionName> and later consumed by the deploy stage when import_config_data=true.
8
JFrog Upload
ppudot2-cloud/GHA-Core/templates/steps/dynamics/jfrog-upload@main
if: inputs.jfrog_url != ''
Uploads the unmanaged ZIP, managed ZIP, and SARIF report to JFrog Artifactory under the path <jfrog_repo>/<SolutionName>/<artifact_name>/. Uses JFROG_TOKEN fetched from AKV in CI Bootstrap. Skipped when jfrog_url is empty or mock_deploy=true. The deploy stage downloads from exactly this path using the same deterministic artifact name.
9
Write build summary
Write-BuildSummary.ps1 · if: always()
Calls Write-BuildSummary.ps1 to append a Markdown table to the GitHub Actions Job Summary ($GITHUB_STEP_SUMMARY). Reports solution name, version, artifact name, and whether the source was from export or the committed tree. Runs even if a previous step fails.
3

Stage 3 — Deploy Chain

A single job that iterates all 6 environments in order using strategy.matrix + max-parallel:1. Each iteration is gated by a GitHub Environment protection rule before deploying all solutions.

Sequential
Design pattern: Instead of 12 static jobs (6 gate + 6 deploy), this stage uses ONE job (deploy-env) with a strategy.matrix over env_matrix_json. The environment: field on the job is the gate. max-parallel: 1 enforces ordering. Array order in env_matrix_json controls promotion sequence.
🔐→🚀 deploy-env (one iteration per environment, strictly sequential) _stage-deploy-chain.yml → jobs.deploy-env

Runs 6 times, once per environment. Before each iteration, GitHub pauses and displays the approval UI for that environment's required reviewers (configured in Settings → Environments → <name>). After approval, the runner is provisioned and the three steps below execute.

1
CI Bootstrap
ppudot2-cloud/GHA-Core/templates/steps/dynamics/ci-bootstrap@main
Full bootstrap on a fresh runner for each environment. Checkout, Azure OIDC, AKV secrets (PP credentials + JFrog token if needed), variable merge. The PP credentials are used by PAC CLI and the blocking-check/version-compare scripts in the subsequent step.
2
Install PAC CLI
ppudot2-cloud/GHA-Core/templates/steps/dynamics/pac-install@main
Installs PAC CLI. Required because this is a new runner — PAC is not persisted between jobs.
3
Deploy all solutions → <EnvName>
ppudot2-cloud/GHA-Core/templates/steps/dynamics/deploy-all-solutions@main
The core composite action. Receives solutions_json (the full solution matrix) and all per-environment and common options. Internally runs a PowerShell loop over every solution. For each solution in sequence:
🔁 Per-solution loop (sequential)
1
PAC auth create
Creates a PAC CLI auth profile named target-<EnvName> using PP_APP_ID, PP_CLIENT_SECRET, PP_TENANT_ID and selects it. All subsequent PAC calls are routed to the target environment.
Skipped when mock_deploy=true
2
JFrog download
Calls Invoke-JFrogAction.ps1 -Action download to download the managed ZIP (and config-data ZIP if present) from JFrog Artifactory into out/<artifact_name>/. Artifact name is computed deterministically as <SolutionName>_<run_number>_<run_attempt> — no build output lookup needed.
Skipped when mock_deploy=true or jfrog_url is empty
3
Token substitution
Reads the deployment-settings JSON file at <deployment_settings_prefix>/<env>/<SolutionName>.json, replaces all #{TOKEN_NAME}# placeholders with matching environment variable values (set during CI Bootstrap from AKV), and writes the resolved file to out/<artifact_name>/deployment-settings-resolved.json.
Skipped when settings file does not exist or mock_deploy=true
4
Verify base solutions
Runs pac solution list --environment <url> and checks that every solution named in base_solutions is present. Fails the pipeline if any required base solution is missing — prevents deployment of a dependent solution before its dependency is installed.
Only when base_solutions is non-empty AND mock_deploy=false
5
Blocking check
Calls Invoke-BlockingCheck.ps1, which queries the target environment's Dataverse API for conditions that would cause an import to fail or corrupt data: active flows that reference the solution, ownership locks, active layer conflicts. The script fails the pipeline if blockers are found.
Only when enable_blocking_check=true AND mock_deploy=false
6
Version compare
Calls Compare-SolutionVersion.ps1, which queries the installed solution version in the target environment and compares it to the artifact version. If the installed version is equal to or higher than the artifact, skip_import is set to true and steps 7–10 are bypassed for this solution.
Only when enable_version_compare=true AND mock_deploy=false
7
Backup
Runs pac solution export --name <name> --managed to export the currently installed managed solution as a pre-deployment backup ZIP to backup/<SolutionName>_<EnvName>_backup.zip on the runner. Useful for rollback. (Not uploaded to GitHub artifacts to keep storage lean — stored only on runner disk for the duration of the job.)
Only when enable_backup=true AND skip_import=false AND mock_deploy=false
8
Import solution
Standard path: pac solution import --path <managed.zip> --publish-all-after-import --force-overwrite plus optional --settings-file if a resolved settings file exists.

Stage-and-upgrade path (when trigger_upgrade=true): pac solution import --import-as-holding to stage the solution as a "holding" layer, then pac solution upgrade --solution-name <name> --async to apply the upgrade and remove the old layer. This pattern avoids downtime for solutions with active customizations.
Skipped when skip_import=true or mock_deploy=true
9
Import config data
Runs pac data import --path config-data/<SolutionName>-data.zip. Imports configuration migration data (look-up values, static reference data) into the environment after the solution has been successfully imported. The data ZIP was exported and packed in Stage 2 Step 7.
Only when import_config_data=true AND skip_import=false AND mock_deploy=false AND data file exists
10
Publish customizations
Runs pac solution publish to flush the Dataverse publishing queue and make all customizations visible. Skipped when trigger_upgrade=true because the upgrade command triggers its own publish internally.
Skipped when trigger_upgrade=true or skip_import=true or mock_deploy=true
11
JFrog prod tag
Calls Invoke-JFrogAction.ps1 -Action tag-prod to set a property prodDeployed=true on the JFrog artifact. This makes it easy to filter for "artifacts that have reached production" in Artifactory queries. Runs only for the Prod environment iteration.
Only when tag_prod_deployed=true (automatically set for Prod) AND mock_deploy=false AND jfrog_url is set
12
Write deploy summary
Calls Write-DeploySummary.ps1 to append a row to the Job Summary table. Reports solution name, version, environment, and whether the import was performed or skipped (due to version compare). Always runs regardless of import outcome.
Failure handling: Each solution's deploy is wrapped in a try/catch. If a solution fails, it is added to a $failed list and processing continues for the remaining solutions. After all solutions are attempted, if $failed is non-empty, the step throws and fails the job. This means you get a single complete report of which solutions failed, rather than stopping at the first failure.
📋

Pipeline Summary Job

Always runs, even if earlier stages failed. Aggregates all job-level summaries into a single report in the GitHub Actions Job Summary tab.

Always

Checks out both repos, downloads all job-summary-* artifacts uploaded during the run (build + deploy summaries), and calls Write-PipelineSummary.ps1 which writes a comprehensive Markdown table to $GITHUB_STEP_SUMMARY. Includes stage results, solution list, run metadata, and commit SHA.

Dispatch Inputs

Provided by the person triggering the pipeline in the GitHub Actions UI (Actions → Combined Pipeline → Run workflow). These are the only inputs a user directly controls at run time.

Input Type Default Description & Effect
solutions string 'all' Controls which solutions enter the pipeline. 'all' reads every entry in solutions.json. A comma-separated list (e.g. 'CoreSolution,ExtensionA') restricts the build + deploy to those solutions only. The topological sort in Resolve-SolutionMatrix.ps1 still enforces dependency order.
skip_export boolean false When true, Stage 1 is skipped and Stage 2 packs from the committed src/solutions/ tree. Use when the committed source already reflects what you want to build (e.g. a release from a PR merge). Useful for faster release-only runs.
mock_deploy boolean false Most powerful toggle. Skips Stage 1 automatically (no export). Runs build and Solution Checker for real but writes no artifacts to JFrog. Simulates the entire deploy chain without importing into any Dataverse environment. Use to validate the pipeline end-to-end safely. Approval gates are bypassed in simulation mode.
trigger_upgrade boolean false Applies to every managed-solution environment (Intg through Prod). When true, the import uses the holding-solution (stage-and-upgrade) pattern: the new solution is imported as a holding layer, then the upgrade is applied asynchronously, removing the previous layer cleanly. Prevents downtime for solutions with active customizations. Has no effect on Unmanaged (Dev).
base_solutions string '' Comma-separated list of solution names that must be installed in the target environment before this solution can be imported. The deploy loop queries pac solution list and fails if any named solution is absent. Applies to every environment. Falls back to vars.PP_BASE_SOLUTIONS if empty.
checker_error_level choice 'HighIssue' Sets the minimum severity that causes Solution Checker to fail the build. Options (from strictest to most lenient): CriticalIssue, HighIssue, MediumIssue, LowIssue, InformationalIssue. Lower-severity issues are reported in the SARIF file but do not block the pipeline.
env_config_override string (JSON) '{}' A JSON patch applied on top of the inline per-environment defaults in the setup step. Keys are lowercase environment names; values are objects with the fields to override. Example: {"uat":{"import_config_data":true},"prod":{"enable_backup":false}}. Only affects this single run — the defaults in the workflow file are unchanged. If the JSON is malformed, a warning is logged and defaults are used unchanged.

Repository Variables

Set in Settings → Secrets and variables → Actions → Variables. These are plaintext values that do not require secrets storage. They are referenced in the workflow via ${{ vars.* }}.

Variable Required Description & Where Used
PP_SDBX_URL ✓ for export URL of the Power Platform sandbox environment. Used in Stage 1 as the source for solution export, and passed to Stage 2 for config-data export. Example: https://myorg-sandbox.crm.dynamics.com.
PP_DEV_URL ✓ Dev environment URL. Embedded into env_matrix_json by the setup step. Used as the target URL for Dev deployments.
PP_INTG_URL ✓ Integration environment URL. Also used as previous_url for UAT (gives version-compare context).
PP_UAT_URL ✓ UAT environment URL. Also used as previous_url for FRS.
PP_FRS_URL ✓ FRS (Functional Regression Suite) environment URL. Also used as previous_url for Perf.
PP_PERF_URL ✓ Performance environment URL. Also used as previous_url for Prod.
PP_PROD_URL ✓ Production environment URL.
PP_SOLUTION_NAME ✗ optional Used by Resolve-SolutionMatrix.ps1 for single-solution repos where no explicit solutions input is provided. If solutions.json is present, this is ignored.
PP_BASE_SOLUTIONS ✗ optional Fallback value for base_solutions when the dispatch input is left empty. Allows a repo-wide default base solution list without requiring the user to type it every run.
JFROG_URL ✗ optional JFrog Artifactory base URL. When set, Stage 2 uploads artifacts after a successful build, and Stage 3 downloads artifacts from JFrog during deploy. When empty, local artifact storage is assumed.
JFROG_REPO ✗ optional JFrog repository name. Defaults to powerplatform-solutions when not set.

Secrets

Set in Settings → Secrets and variables → Actions → Secrets. Encrypted at rest; never visible in logs. Accessed via ${{ secrets.* }} in workflows, or fetched from Azure Key Vault during CI Bootstrap.

Important: PP_APP_ID, PP_CLIENT_SECRET, and PP_TENANT_ID are not stored directly as GitHub Secrets in this pipeline. They are stored in Azure Key Vault and fetched by CI Bootstrap into GITHUB_ENV at the start of every job. This means the composite actions can access them as environment variables without GitHub Secrets being passed through reusable workflow boundaries.
Secret Description & Where Used
GHA_CORE_PAT GitHub Personal Access Token with read:packages and contents:read on the GHA-Core repo. Used by every CI Bootstrap call to check out GHA-Core into .ci/. Must be a PAT (not GITHUB_TOKEN) because cross-repo access is required. Stored as a GitHub Secret and passed via env: GHA_CORE_PAT on the composite action step (composite actions cannot access secrets.* directly).
PP_APP_ID (in AKV) Service principal Application ID with Power Platform Administrator role on all environments. Fetched from Azure Key Vault by CI Bootstrap. Used by PAC CLI commands, Invoke-BlockingCheck.ps1, Compare-SolutionVersion.ps1, and the microsoft/powerplatform-actions/* actions.
PP_CLIENT_SECRET (in AKV) Client secret for the service principal. Fetched from AKV. Never logged.
PP_TENANT_ID (in AKV) Azure AD Tenant ID for the service principal. Fetched from AKV.
JFROG_TOKEN (in AKV) JFrog API token for uploading and downloading artifacts. Fetched from AKV only when jfrog_enabled=true is passed to CI Bootstrap (i.e. when JFROG_URL is set). Used by Invoke-JFrogAction.ps1 in both Stage 2 (upload) and Stage 3 (download + prod tag).

Inline Environment Configuration

Per-environment deploy options are defined inline inside combined-pipeline.yml in the setup job's "Build environment matrix" step. There is no external config file — edit this block directly to change permanent defaults.

Fields per environment entry

Field Type Description & Effect
name string Must exactly match a GitHub Environment configured in Settings → Environments. This value is used as the environment: on the deploy-env job, triggering the protection rule and approval gate.
url string Power Platform environment URL. Populated from the corresponding vars.PP_*_URL repo variable at setup time. Passed to PAC CLI as the target for all deploy operations.
previous_url string URL of the environment immediately before this one in the promotion chain (e.g. Intg's previous_url is Dev's URL). Passed to the deploy action for informational and version-compare context. Empty for Dev (no predecessor).
solution_type string Unmanaged for Dev only (allows customization in the dev environment). Managed for all other environments (locks the solution against customization, as required by best practice).
enable_backup boolean When true, exports the currently installed solution from the target environment as a backup ZIP before importing the new version. Default true for UAT, FRS, Prod; false for Dev, Intg, Perf.
enable_blocking_check boolean When true, runs Invoke-BlockingCheck.ps1 to detect active flows, ownership locks, or layer conflicts before importing. Default false for Dev; true for all others.
enable_version_compare boolean When true, runs Compare-SolutionVersion.ps1 to check the installed version. If the installed version ≥ artifact version, the import is skipped (avoids redundant re-imports). Default false for Dev and Intg; true for UAT, FRS, Perf, Prod.
import_config_data boolean When true, runs pac data import after the solution import. Default true for Prod only. Typically enabled for Prod because reference/configuration data needs to be current in production.

Overriding for a single run

Pass a JSON patch in the env_config_override dispatch input. Keys are lowercase environment names. Only the specified fields are overridden; all others keep their defaults.

// Example: enable config data import for UAT in this run only,
// and disable backup for Prod
{
  "uat":  { "import_config_data": true },
  "prod": { "enable_backup":      false }
}

Input Precedence Rules

When the same concept can be configured in multiple places, this table shows which value wins.

1
Dispatch Input (run-time override)
Values typed in the GitHub Actions UI when triggering the workflow. Wins over everything for global options like mock_deploy, trigger_upgrade, checker_error_level. For per-env options, wins via env_config_override JSON patch.
HIGHEST PRIORITY
2
env_config_override (JSON patch)
Per-environment fields passed in env_config_override are merged on top of the inline defaults in the setup step. Only the fields explicitly included in the patch are changed; other fields keep their inline default values.
3
Inline defaults in combined-pipeline.yml
The $envMatrix block in the "Build environment matrix" setup step. These are the permanent defaults for each environment. Edit this block to change defaults for all future runs without needing to pass overrides each time.
4
Reusable workflow / action defaults
Default values declared in on.workflow_call.inputs in the GHA-Core stage files and in composite action input definitions. These only take effect when a caller does not pass a value at all. Never override a caller's explicit input.
LOWEST PRIORITY

Precedence by variable category

Variable Declared In Highest-Priority Source Notes
solutions dispatch input Dispatch input (user types it) Defaults to 'all'. There is no repo variable fallback.
skip_export dispatch input Dispatch input mock_deploy=true also forces skip_export behavior regardless of this value.
mock_deploy dispatch input Dispatch input Most impactful flag. Implicitly sets skip_export=true and disables all Dataverse + JFrog operations.
trigger_upgrade dispatch input Dispatch input Single global toggle — applies to all environments. There is no per-environment override for this option.
base_solutions dispatch input then vars.PP_BASE_SOLUTIONS Dispatch input wins; falls back to vars.PP_BASE_SOLUTIONS Expression in workflow: ${{ inputs.base_solutions || vars.PP_BASE_SOLUTIONS || '' }}. The || chain means dispatch input takes priority, then the repo variable, then empty string.
checker_error_level dispatch input Dispatch input Defaults to 'HighIssue'. No repo variable fallback — the dispatch dropdown always shows the current value.
PP_*_URL (env URLs) repo variable Repo variable only Embedded into env_matrix_json at setup time. Cannot be overridden per-run via env_config_override (only behavioral flags can be patched, not URLs).
solution_type inline default then env_config_override env_config_override patch wins over inline default E.g. override Intg to Unmanaged for a testing run: {"intg":{"solution_type":"Unmanaged"}}.
enable_backup inline default then env_config_override env_config_override patch wins Inline defaults: false for Dev/Intg/Perf, true for UAT/FRS/Prod.
enable_blocking_check inline default then env_config_override env_config_override patch wins Inline defaults: false for Dev, true for all others.
enable_version_compare inline default then env_config_override env_config_override patch wins Inline defaults: false for Dev/Intg, true for UAT/FRS/Perf/Prod.
import_config_data inline default then env_config_override env_config_override patch wins Inline default: true for Prod only. Requires a valid data_schema_file in solutions.json for the config data to be exported in Stage 2.
jfrog_url / jfrog_repo repo variable Repo variable only Cannot be overridden per-run. To test without JFrog, leave JFROG_URL empty in the repo variables — all JFrog-dependent steps skip automatically.
PP_APP_ID / CLIENT_SECRET / TENANT_ID Azure Key Vault AKV only — no override possible Fetched by CI Bootstrap. The single service principal is used across all environments. Environment-specific authentication is not supported in this design.
run_number / run_attempt github context GitHub context — not configurable Used to build the deterministic artifact name <SolutionName>_<run_number>_<run_attempt>. Consistent across all stages — the build uploads and the deploy downloads using the same name without any handoff variable.
Quick reference — what to change where:

Change a URL permanently → Edit vars.PP_*_URL in repo Settings.
Change a per-env default permanently → Edit the $envMatrix block in combined-pipeline.yml setup step.
Override a per-env option for one run → Pass env_config_override JSON at dispatch.
Override a global option for one run → Pass the relevant dispatch input (e.g. trigger_upgrade=true).
Validate the full pipeline without touching Dataverse → Set mock_deploy=true at dispatch.
