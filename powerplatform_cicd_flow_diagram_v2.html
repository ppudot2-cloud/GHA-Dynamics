Key design decisions:
• Gate jobs separate from deploy matrix — a lightweight job with environment: Intg (no matrix) is placed BEFORE the deploy matrix job. This means one approval covers all N solutions. Without this pattern, GitHub would require N approvals for an N-solution matrix.
• Parallel build, sequential deploy — build jobs fan out in parallel (no ordering needed); deploy jobs use max-parallel: 1 to prevent Dataverse async operation conflicts when multiple solutions import simultaneously.
• Deterministic artifact naming — artifact name solution-{name}-{run_number} is computed identically in build and deploy jobs. No matrix output collection needed — deploy simply reconstructs the name.
• Single PR for multi-solution export — a separate create-pr job runs AFTER the entire export matrix completes, creating one PR that lists all exported solutions. Plus: git pull --rebase in each matrix instance prevents conflicts on the shared branch.

🔢 solutions-config.json — Dependency Ordering

When do you need this file? Only when you have solutions with dependencies — e.g., ExtensionA imports types from CoreSolution and must deploy after it. Without this file, solutions deploy in alphabetical order, which may break if ExtensionA alphabetically precedes CoreSolution.

How ordering works

StepDescription
1. Parse configRead solutions array from .github/solutions-config.json
2. Filter selectedKeep only entries that are in the user's requested solutions set
3. Append unlistedSolutions in the requested set but NOT in config are appended alphabetically after listed ones
4. Output matrixFinal ordered array becomes the job matrix

🔄 How Matrix + max-parallel:1 Prevents Conflicts

Why parallel build (no max-parallel)?
Build jobs are independent — packing CoreSolution doesn't affect ExtensionA's pack. Running them in parallel halves build time for 2 solutions, cuts it by 75% for 4.
Why sequential deploy (max-parallel:1)?
Dataverse async operations are per-environment. If two solutions import simultaneously, each triggers flows, plugin registrations, and metadata updates. These can conflict, causing unpredictable failures. Sequential deploys guarantee each solution fully settles before the next one starts.

🔀 Export — Sequential with git pull --rebase

Why max-parallel:1 for export?
All export matrix instances commit to the same branch. If they ran in parallel:
• Instance A and Instance B both checkout the branch
• Both commit their solution files
• Instance A pushes successfully
• Instance B's push fails — remote has diverged

With max-parallel:1, instances run sequentially. Before each commit, the instance runs git pull --rebase to incorporate any commits already pushed by previous instances.
Sequential export timeline (3 solutions):
[CoreSolution export job]
  git checkout export/branch
  export + unpack
  git pull --rebase
  git commit + push ✓
↓
[ExtensionA export job]
  git checkout export/branch
  export + unpack
  git pull --rebase     ← picks up CoreSolution commit
  git commit + push ✓
↓
[create-pr job]
  gh pr create (one PR for all)

Security Scan Toggle Logic
How lowcode-nocode master flag, individual toggles, and Solution Checker interact

🔒 Three-Level Scan Model

🔵 BlackDuck SCA
What: Open-source composition analysis. Finds known CVEs in third-party components.

When: lowcode-nocode == 'true' AND enable-blackduck == 'true'

Default: enable-blackduck = true (but disabled by lowcode-nocode master toggle)

Action: synopsys-sig/detect-action@v1.3.1
🔴 Checkmarx SAST
What: Static application security testing. Finds vulnerabilities in custom code (plugins, PCF controls, scripts).

When: lowcode-nocode == 'true' AND enable-checkmarx == 'true'

Default: enable-checkmarx = true (but disabled by master toggle)

Action: checkmarx/ast-github-action@main
🔴 Solution Checker
ALWAYS ON
What: Power Apps Solution Checker. Validates platform-specific rules, patterns, and best practices.

When: ALWAYS — no if: condition. Cannot be disabled by any toggle.

Blocks pipeline: Yes — fail-on-analysis-error: true

Action: check-solution@v1

⚙️ Deployment Settings File Resolution

Multi-solution path (preferred): deployment-settings/{env}/{SolutionName}.json
Legacy fallback: deployment-settings/{env}/deployment-settings.json
Graceful skip: If neither exists, the deploy proceeds without deployment settings.
Resolution logic in _reusable-deploy.yml (bash step settings-file):
REQUESTED = inputs.deployment-settings-file
  # e.g. "deployment-settings/dev/CoreSolution.json"

if REQUESTED != "" AND file exists:
  → output.path = REQUESTED, output.exists = true

elif REQUESTED != "" AND file NOT found:
  LEGACY = dirname(REQUESTED) + "/deployment-settings.json"
  if LEGACY exists:
    → output.path = LEGACY, output.exists = true
  else:
    → output.exists = false

# Import step uses:
use-deployment-settings-file: steps.settings-file.outputs.exists == 'true'
deployment-settings-file: steps.settings-file.outputs.path || ''
