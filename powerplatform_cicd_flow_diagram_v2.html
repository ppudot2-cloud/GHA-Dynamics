Key design decisions:
• Thin wrapper + vars.* boundary — vars.* (repository variables) cannot cross repository boundaries in reusable workflow_call. GHA-Dynamics wrappers read their own vars.* and pass them as explicit string inputs to GHA-Core. All CI/CD logic lives in GHA-Core; wrappers only expose UI and forward variables.
• GHA pipeline artifacts as primary deploy source — build jobs upload to actions/upload-artifact@v4 (solution-{name}-{run#}). Deploy jobs download via actions/download-artifact@v4. JFrog still receives uploads in build (for traceability) and is tagged after Prod success, but is NOT used as the deploy-time download source.
• Solution-scoped backup — backup uses export-solution@v1 instead of backup-environment@v1. Scope: one solution, not the full environment. Artifact naming: backup-{solution}-{env}-v{run#}, retained 30 days. Rollback re-imports this ZIP via import-solution@v1.
• Warn-only blocking check — Invoke-BlockingCheck.ps1 emits ::warning:: annotations when async ops are in flight, but never exit 1. Pipeline always continues. Blocking count is output so downstream summary can display it.
• Per-job JSON summaries — each build and deploy job uploads a JSON record artifact (job-summary-*). The final pipeline-summary job downloads all records (pattern: job-summary-*, merge-multiple: true) and renders a consolidated table via Write-PipelineSummary.ps1.
• Gate jobs separate from deploy matrix — a lightweight job with environment: Intg (no matrix) is placed BEFORE the deploy matrix job. This means one approval covers all N solutions. Without this pattern, GitHub would require N approvals for an N-solution matrix.
• Parallel build, sequential deploy — build jobs fan out in parallel; deploy jobs use max-parallel: 1 to prevent Dataverse async conflicts when multiple solutions import simultaneously.

When do you need this file? Only when solutions have dependencies — e.g., ExtensionA imports types from CoreSolution and must deploy after it. Without this file, solutions deploy in alphabetical order.

📊 Per-Job Summaries & Consolidated Pipeline Report

Why not use GITHUB_STEP_SUMMARY directly?
GITHUB_STEP_SUMMARY is write-only and job-scoped. No job can read another job's summary content. To aggregate across all N build and M deploy jobs, each job writes a JSON record to a file and uploads it as a named artifact (job-summary-{type}-{solution}-{run#}).
Consolidated pipeline-summary job:
After all deploy stages complete, the pipeline-summary job downloads all job-summary-* artifacts (pattern match, merge-multiple: true), then calls Write-PipelineSummary.ps1 -JobSummariesDir job-summaries/ which reads the JSON records and renders Build Details + Deployment Details tables.

How lowcode-nocode master flag, individual toggles, and Solution Checker interact

🔒 Three-Level Scan Model

🔵 BlackDuck SCA
What: Open-source composition analysis. Finds known CVEs in third-party components.

When: lowcode-nocode == 'true' AND enable-blackduck == 'true'

Default: enable-blackduck = true (but disabled by lowcode-nocode master toggle)

Action: synopsys-sig/detect-action@v1.3.1

What: Static application security testing. Finds vulnerabilities in custom code (plugins, PCF controls, scripts).

When: lowcode-nocode == 'true' AND enable-checkmarx == 'true'

Action: checkmarx/ast-github-action@main

ALWAYS ON

Repository Structure & Settings Files
Two-repo split (GHA-Dynamics + GHA-Core), deployment settings resolution, and environment gate setup

📁 Two-Repository Architecture

Why two repos? GitHub Actions reusable workflows (workflow_call) cannot read vars.* (repository variables) from the calling repository. The thin wrapper pattern solves this: GHA-Dynamics wrappers read their own vars.* and pass them as explicit string inputs. All reusable logic that needs no variable access lives in GHA-Core.

⚙️ Deployment Settings File Resolution

Multi-solution path (preferred): deployment-settings/{env}/{SolutionName}.json
Legacy fallback: deployment-settings/{env}/deployment-settings.json
Graceful skip: If neither exists, the deploy proceeds without deployment settings.
Resolution logic in _reusable-deploy.yml (bash step settings-file):
REQUESTED = inputs.deployment-settings-file
  # e.g. "deployment-settings/dev/CoreSolution.json"

if REQUESTED != "" AND file exists:
  → output.path = REQUESTED, output.exists = true

elif REQUESTED != "" AND file NOT found:
  LEGACY = dirname(REQUESTED) + "/deployment-settings.json"
  if LEGACY exists:
    → output.path = LEGACY, output.exists = true
  else:
    → output.exists = false

# Import step uses:
use-deployment-settings-file: steps.settings-file.outputs.exists == 'true'
deployment-settings-file: steps.settings-file.outputs.path || ''
