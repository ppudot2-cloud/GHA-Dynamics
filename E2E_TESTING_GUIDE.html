Overview & What You're Building

Understand the full test topology before you start

By the end of this guide you will have a fully operational CI/CD pipeline that automatically builds, scans, and deploys two real Power Platform solutions through four environments. Here's the complete topology:

🔵 Dev (Source)
your-org-dev.crm.dynamics.com
Sandbox Used to export solution source. The pipeline reads from this environment when exporting config data.
🟡 Test / INTG
your-org-intg.crm.dynamics.com
Sandbox First automated deploy target. No approval required. Validates the managed solution imports cleanly.
🟠 UAT
your-org-uat.crm.dynamics.com
Sandbox Second deploy target. Manual approval required (you approve in GitHub). User acceptance testing.
🔴 Prod
your-org-prod.crm.dynamics.com
Production Final target. Two-approver gate. On success the JFrog artifact is tagged prodDeployed=true.

What the pipeline does end-to-end

  1. Build job — packs both solutions with PAC CLI, stamps the version from Solution.xml, runs Solution Checker (real scan, not mock), exports config data, and uploads the full package to JFrog Artifactory.
  2. Deploy DEV — downloads the managed ZIP from JFrog, imports it to the Dev environment, applies deployment settings, runs a smoke-test ping.
  3. Deploy INTG — same as Dev, auto-triggered.
  4. Deploy UAT — waits for your approval in GitHub before deploying.
  5. Deploy PROD — waits for approval, deploys, then tags the JFrog artifact with prodDeployed=true;deployedDate=<date>.
💡 Start with mock_deploy=true Once GitHub and Azure are wired up but before PP environments exist, run the pipeline with mock_deploy: true. All steps run as simulations — no real PAC CLI, no real imports. This lets you validate the workflow YAML syntax and GitHub configuration without needing any actual Power Platform environments.
✅

Prerequisites

Make sure you have all of these before starting
  • An Azure subscription where you have Owner or Contributor + User Access Administrator rights
  • A Microsoft 365 / Entra ID tenant — used for the App Registration (can be the same tenant as Azure)
  • Power Platform Admin access — you need the Environment Admin or Global Admin role in the Power Platform Admin Center
  • A GitHub repository — the GHA-Dynamics repo you've been working on. You need Admin access to configure Environments and Secrets.
  • JFrog Artifactory — either a cloud account at jfrog.io or an on-premise instance. A free cloud trial at jfrog.com/start-free is sufficient for testing. You need API key access and a Generic repository.
  • PAC CLI installed locally (optional but helpful) — winget install Microsoft.PowerPlatform.CLI — lets you test packing solutions before pushing to GitHub.
  • The GHA-Core repo cloned and pushed to your GitHub org alongside GHA-Dynamics.
⚠️ Use Sandbox environments for testing — not Production licenses Power Platform Sandbox environments consume capacity from your tenant. For isolated testing you can create Trial environments (30-day free, no license needed) in the Power Platform Admin Center. Use Trial type for Dev, INTG, and UAT — reserve Sandbox or Production type for the Prod environment.

Create the Azure App Registration

The identity that GitHub Actions uses to talk to Azure and Power Platform

The App Registration is a service principal (SPN) in Entra ID. The pipeline uses it in two ways: (1) OIDC login to Azure to fetch secrets from Key Vault, and (2) as the identity imported into each Power Platform environment to perform solution imports.

💡 No stored secrets — OIDC only We use Workload Identity Federation (OIDC) so GitHub Actions can authenticate to Azure without storing a client secret anywhere. GitHub presents a short-lived JWT token; Azure validates it against a Federated Identity Credential on the App Registration. Nothing to rotate.

Step 1 — Create the App Registration

Azure Portal › Entra ID › App registrations › New registration
1
Name

Enter a descriptive name, e.g. sp-powerplatform-cicd-gha. This will be visible in audit logs.

2
Supported account types

Select Accounts in this organizational directory only (Single tenant).

3
Redirect URI

Leave blank. Click Register.

4
Copy the IDs — you'll need these later

On the Overview page, copy and save these three values:

  • Application (client) ID → this becomes AZURE_CLIENT_ID and PP_APP_ID in Key Vault
  • Directory (tenant) ID → this becomes AZURE_TENANT_ID and PP_TENANT_ID in Key Vault
  • Object ID → needed when creating the PP Application User

Step 2 — Add API Permissions

App Registration › API permissions › Add a permission
5
Add Dynamics CRM permission

Click Add a permission → APIs my organization uses. Search for Dataverse (or Common Data Service). Select it, choose Delegated permissions, and check user_impersonation. Click Add permissions.

6
Grant admin consent

Click Grant admin consent for [Your Tenant] and confirm. The permission status should show a green checkmark — Granted for [Tenant].

Step 3 — Create a Client Secret (for Power Platform auth only)

App Registration › Certificates & secrets › New client secret
7
Create the secret

Add a description like pp-cicd-secret, set expiry to 24 months, and click Add.

8
⚠️ Copy the secret VALUE immediately

The secret value is only shown once. Copy it now and paste it somewhere safe (you'll add it to Key Vault in the next section). The format looks like: abc123~XYZ.something.long_string

Step 4 — Configure OIDC Federated Identity Credential

App Registration › Certificates & secrets › Federated credentials › Add credential
9
Select scenario: GitHub Actions deploying Azure resources
10
Fill in the GitHub details
FieldValue
OrganizationYour GitHub org or username (e.g. contoso-corp)
RepositoryGHA-Dynamics
Entity typeBranch
Branchmain
Namegha-dynamics-main

Click Add. Repeat for any other branches (e.g. release/*) that will trigger the pipeline.

Step 5 — Assign Azure Role to the SPN

The SPN needs permission to read secrets from Key Vault. Assign it at the Key Vault resource level (done in the next section), not at subscription level.

✅ App Registration complete You now have a Client ID, Tenant ID, Object ID, and Client Secret. Keep them — you'll add them to Key Vault next.

Create Azure Key Vault & Add Secrets

Central secrets store — the pipeline fetches all credentials from here at runtime

Step 1 — Create the Key Vault

Azure Portal › Key vaults › Create
1
Basics
FieldValue
SubscriptionYour test subscription
Resource groupCreate new: rg-pp-cicd-test
Key vault namekv-pp-cicd-test (must be globally unique)
RegionAny — pick the closest region
Pricing tierStandard
2
Access configuration — use Azure RBAC

On the Access configuration tab, select Azure role-based access control. This is more secure than Vault Access Policies and works well with OIDC. Click Review + create → Create.

Step 2 — Grant the SPN access to the Key Vault

Key Vault › Access control (IAM) › Add role assignment
3
Assign Key Vault Secrets User role

Role: Key Vault Secrets User. Members: search for the App Registration name (sp-powerplatform-cicd-gha). Click Review + assign.

This grants the SPN read-only access to secrets — the minimum needed for the pipeline.

Step 3 — Add the pipeline secrets

Key Vault › Secrets › Generate/Import

Create each of the following secrets. Use Manual upload type. The Name column is the exact secret name the pipeline expects.

Secret Name (exact) Value to paste Notes
pp-app-id The Application (client) ID from Step 4 above GUID format: xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
pp-client-secret The client secret VALUE you copied in Step 8 The long random string — not the secret ID
pp-tenant-id The Directory (tenant) ID from Step 4 GUID format
jfrog-api-key Your JFrog API key (from JFrog → User profile → Generate API key) If you don't have JFrog yet, enter a placeholder and update later
⚠️ Secret names are case-sensitive and must match exactly The pipeline script looks for pp-app-id, pp-client-secret, pp-tenant-id, and jfrog-api-key — lowercase with hyphens. Any variation will cause the Fetch Secrets step to fail with an AKV 404 error.
✅ Key Vault complete Note down the Key Vault name (e.g. kv-pp-cicd-test) — you'll add it to GitHub Variables in Section 5.

Create Power Platform Environments

Four environments — Dev, Test (INTG), UAT, Prod — plus Application Users in each

Step 1 — Create the four environments

Power Platform Admin Center › admin.powerplatform.microsoft.com › Environments › New

Create each environment with the settings below. For testing, use Trial type to avoid consuming production capacity. Each takes 2–5 minutes to provision.

Name Type Purpose Dataverse Suggested URL slug
Contoso Dev Trial / Sandbox Source environment (export config data from here) ✅ Enable contoso-dev
Contoso INTG Trial / Sandbox First automated deploy target ✅ Enable contoso-intg
Contoso UAT Trial / Sandbox User acceptance, manual-approval gate ✅ Enable contoso-uat
Contoso Prod Production / Sandbox Production target, two-approver gate ✅ Enable contoso-prod
💡 How to create each environment In the New Environment wizard: (1) Set the name and type. (2) Turn on Add a Dataverse data store. (3) Set Language = English, Currency = USD (or your currency). (4) Leave the URL as suggested or enter your slug. (5) Click Save and wait for provisioning to complete before creating the next one.

Step 2 — Record the environment URLs

After each environment is provisioned, click into it in the Admin Center and copy the Environment URL. It looks like:

https://contoso-dev.crm.dynamics.com

You need all four URLs — they go into project-vars.yml and GitHub Variables in the next steps.

Step 3 — Create the Application User in each environment

The Application User is how the App Registration (SPN) gets permission to import solutions in each environment. You must create it separately in all four environments.

Power Platform Admin Center › Environments › [Select Environment] › Settings › Users + permissions › Application users › New app user
1
Select the App Registration

Click Add an app and search for your App Registration name (sp-powerplatform-cicd-gha). Select it and click Add.

2
Set the Business Unit

Select the root business unit (the top-level one, usually the name of your org).

3
Assign the System Administrator security role

Under Security roles, click the edit (pencil) icon. Select System Administrator. This gives the SPN full access to import and manage solutions.

4
Click Create and repeat for all four environments

Do this for Dev, INTG, UAT, and Prod. Each takes about 30 seconds. The Application User status should show Enabled.

❌ Common mistake — wrong identity added Make sure you add the App Registration (service principal), not a regular user. The Application Users page only accepts AAD app registrations. If you search and don't find it, ensure the App Registration exists in the same tenant as your Power Platform environments.
✅ Power Platform setup complete You now have 4 environments, each with the SPN registered as a System Administrator Application User. The pipeline can now import solutions into all four environments.

Configure GitHub Repository

Variables, the bootstrap secret, and environment protection rules

Step 1 — Add Repository Variables (non-sensitive)

GitHub Repository › Settings › Secrets and variables › Actions › Variables tab › New repository variable

These are non-sensitive resource identifiers — safe to store as Variables (not Secrets). Add each one:

Variable Name Value Where to get it
AZURE_CLIENT_ID Application (client) ID of the App Registration Entra ID → App Registrations → your app → Overview
AZURE_TENANT_ID Directory (tenant) ID Same page as above
AZURE_SUBSCRIPTION_ID Your Azure subscription ID Azure Portal → Subscriptions
AZURE_KEY_VAULT_NAME kv-pp-cicd-test The Key Vault name you created in Section 2
JFROG_URL https://your-company.jfrog.io/artifactory JFrog → Settings → Platform → Artifactory base URL
JFROG_REPO powerplatform-solutions The Generic repository you created in JFrog

Step 2 — Add the Bootstrap Secret

GitHub Repository › Settings › Secrets and variables › Actions › Secrets tab › New repository secret
Secret Name Value Purpose
GHA_CORE_PAT A GitHub Personal Access Token with repo scope Used to checkout the GHA-Core shared scripts repository. This is the only secret stored directly in GitHub — everything else comes from Azure Key Vault.
💡 How to create the PAT Go to GitHub → Profile → Settings → Developer settings → Personal access tokens → Tokens (classic) → Generate new token. Set expiry to 90 days (for testing) or 1 year. Check the repo scope. Copy the token immediately and paste it as the GHA_CORE_PAT secret value.

Step 3 — Create GitHub Environments with Protection Rules

GitHub Repository › Settings › Environments › New environment

Create four environments. The name must match exactly what's used in release-pipeline.yml.

Environment Name Required Reviewers Wait Timer Notes
dev None None Auto-deploy after build passes
intg None None Auto-deploy after Dev passes
uat Add yourself as reviewer Optional: 0 min Manual approval gate — you'll get a GitHub notification to approve
prod Add 2 reviewers (yourself + a colleague, or yourself twice) Optional: 5 min Two-person approval for production. Wait timer gives a last-chance cancel window.
1
For each environment: click New environment → type the name → click Configure environment

Then under Deployment protection rules, check Required reviewers for UAT and Prod, and add the reviewers.

2
For the prod environment: add deployment branches restriction

Under Deployment branches and tags, click Add deployment branch rule. Select Selected branches and add main. This prevents anyone from deploying to Prod from a feature branch.

✅ GitHub configuration complete The repository now has 6 variables, 1 secret, and 4 environments with appropriate protection rules.

Run the Pipeline

First a mock run to validate wiring, then a full live run

Phase 1 — Mock Run (validate GitHub wiring first)

Run with mock_deploy: true first. This skips PAC CLI, Power Platform connections, and JFrog network calls — everything runs as a simulation. If it passes, your GitHub YAML, variables, secrets, and environment names are all correct.

1
Trigger a manual workflow run

Go to your GitHub repository → Actions tab → select release-pipeline → click Run workflow (top-right dropdown).

2
Set inputs for the mock run
InputValue for mock
mock_deploytrue
enable_jfrog_uploadtrue (JFrog will be simulated)
3
Click Run workflow and watch the run

You should see the following jobs appear: setup → build (ContosoCRM) and build (ContosoHelpDesk) in parallel → deploy-dev for each → deploy-intg → (pending approval) deploy-uat.

4
Approve the UAT deployment when prompted

You'll get a GitHub notification. Click into the workflow run → click Review deployments → check uat → click Approve and deploy.

5
Verify all stages pass ✅

The mock run should complete fully green. The JFrog tag step is skipped in mock mode (by design). Check the GitHub Step Summary for the Build Results table — it should show 🧪 Simulated for all rows.

Phase 2 — Full Live Run

⚠️ Prerequisite checklist before live run
  • All four PP environments are provisioned and Application Users created ✅
  • Key Vault has all 4 secrets (pp-app-id, pp-client-secret, pp-tenant-id, jfrog-api-key) ✅
  • GitHub has all 6 variables and GHA_CORE_PAT secret ✅
  • project-vars.yml has real environment URLs ✅
  • Mock run passed ✅
1
Trigger Run workflow with mock_deploy = false

Actions → release-pipeline → Run workflow → set mock_deploy: false → Run workflow.

2
Watch the Pre-flight Validation step

This is Step 2 in the Build job. It should print a validation report across 5 sections. If any section shows ❌, the build fails here — before any expensive operations run. Fix the reported issues and re-run.

3
Watch Solution Checker run (takes 3–10 minutes)

For a real run, the Solution Checker submits the packed solution to the Microsoft Power Platform analysis service. It will pass for these sample solutions (no deprecated APIs, no hard-coded URLs, no XRM SDK violations).

4
Watch the JFrog upload step

After Solution Checker passes, the pipeline uploads the managed ZIP + unmanaged ZIP + SARIF report + config ZIP as a single package to JFrog. You can verify in your JFrog UI under the powerplatform-solutions repository.

5
Watch deployments to Dev and INTG (automatic)

Each deploy job downloads the managed ZIP from JFrog, applies the deployment settings JSON for that environment, and imports the solution into Power Platform. Check in the PP Admin Center → Environments → Solutions — both ContosoCRM and ContosoHelpDesk should appear as Installed.

6
Approve UAT deployment

GitHub sends you an email notification when the UAT deployment is waiting. Click Review deployments in the Actions run → approve. The deployment runs and the solution is imported into the UAT environment.

7
Approve Prod deployment and watch JFrog tagging

Same approval flow for Prod (requires 2 approvers if configured that way). After Prod succeeds, the jfrog-tag-prod job runs automatically and tags the artifact with prodDeployed=true;deployedDate=YYYY-MM-DD in JFrog.

Troubleshooting

The most common failures and how to fix them
Error / Symptom Likely Cause Fix
Pre-flight §5: PP_APP_ID is empty AKV secret pp-app-id not found or SPN doesn't have Key Vault Secrets User role Check Key Vault → Secrets → confirm pp-app-id exists. Check AKV → Access control (IAM) → confirm the SPN has Key Vault Secrets User role assignment.
Azure Login step fails: AADSTS70021 Federated credential subject doesn't match the triggering branch/event Check the Federated Identity Credential in Entra ID. The Subject must match the actual branch/event that triggered the workflow. Add additional credentials for different branches if needed.
Pre-flight §4: JFrog connectivity check FAILED Wrong JFrog URL, wrong API key, or JFrog instance not reachable Test the URL manually: curl -H "X-JFrog-Art-Api: YOUR_KEY" https://YOUR_URL/api/system/ping — should return OK. Verify the jfrog-api-key secret in AKV matches the API key shown in JFrog → User profile.
Solution Checker fails: unauthorized or 403 pp-app-id / pp-client-secret don't match a valid App Registration, or the App Registration doesn't have Dataverse API permissions Verify the client ID and secret in AKV are correct. Check the App Registration → API permissions → Dataverse user_impersonation is granted.
Deploy step: The user is not a member of the organization Application User not created in the target PP environment Go to PP Admin Center → the failing environment → Settings → Application Users. Confirm the SPN appears and has System Administrator role. If missing, re-create it.
Deploy step: solution already installed with same version Version 1.0.0.0 is already installed in the environment from a previous run Bump the version in src/solutions/ContosoCRM/Other/Solution.xml from 1.0.0.0 to 1.0.1.0 and commit. The pipeline reads the version directly from Solution.xml.
UAT approval never shows up GitHub environment not configured as a required reviewer, or the environment name in the workflow doesn't match Check Settings → Environments → uat → Required reviewers is enabled and you're listed. Verify the environment: key in the deploy-uat job in release-pipeline.yml exactly matches uat.
Error: GHA_CORE_PAT secret not set Bootstrap secret missing Settings → Secrets → Actions → confirm GHA_CORE_PAT exists. If the PAT expired (90-day tokens), generate a new one and update the secret.
Build fails: solution_source_folder does not exist The matrix source_folder path doesn't match the actual folder structure in the repo Verify the path in the pipeline matrix matches the actual folder path. For the sample solutions: src/solutions/ContosoCRM and src/solutions/ContosoHelpDesk.
PAC CLI pack fails with null reference Solution.xml is malformed or missing required fields Validate the Solution.xml locally: pac solution pack --folder src/solutions/ContosoCRM --zip /tmp/test.zip --packagetype Unmanaged. The error message will point to the specific invalid element.

Quick diagnostic commands

# Test Azure OIDC login (run in a workflow or Cloud Shell) az login --federated-token "$ACTIONS_ID_TOKEN_REQUEST_TOKEN" ... # Test AKV access az keyvault secret show --vault-name kv-pp-cicd-test --name pp-app-id --query value -o tsv # Test JFrog connectivity curl -s -o /dev/null -w "%{http_code}" \ -H "X-JFrog-Art-Api: YOUR_API_KEY" \ "https://your-company.jfrog.io/artifactory/api/system/ping" # Expected output: 200 # Pack a solution locally with PAC CLI pac solution pack \ --folder src/solutions/ContosoCRM \ --zip /tmp/ContosoCRM_unmanaged.zip \ --packagetype Unmanaged
