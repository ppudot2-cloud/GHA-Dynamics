Key design decisions in this pipeline:
Artifact handoff: Stage 2 uploads solution-artifact-* to GitHub storage (7-day retention). Every deploy env downloads the same ZIPs — JFrog is archival only, downloaded zero times during deploy.
Sequential by deployOrder: solutions.json deployOrder integer controls import sequence. dependsOn is documentation metadata only — no topological sort.
Env config as structured inputs: Each environment has its own named JSON input (dev_config, intg_config, …) in combined-pipeline.yml's with: block — no external file, no setup step PowerShell.
Single deploy job: strategy.matrix + max-parallel:1 + environment: collapses 12 static gate+deploy jobs into 1 job definition. GitHub Environment protection rules provide the approval gates automatically.
JFrog Prod tag: Only the Prod iteration calls JFrog (tag_prod_deployed=true) to mark the artifact as production-deployed. All other envs never touch JFrog.
fail-fast:true on deploy chain: If any environment fails, the entire promotion chain stops. You cannot deploy Prod if UAT failed.

These inputs are defined directly in the stage-deploy job's with: block in combined-pipeline.yml. Each is a compact JSON object. ${{ vars.PP_*_URL }} expressions are substituted by GitHub Actions before the inputs are passed. Edit these to permanently change environment defaults — no external file needed.

Field Reference

🏷️ Per-env JSON fields JSON string input
nameMust exactly match a GitHub Environment in repo Settings → Environments. This is what triggers the protection rule gate.
urlPower Platform environment URL. Set via repo Variables (PP_DEV_URL etc.). Expression substituted before passing.
previous_urlURL of the prior environment — used by Compare-SolutionVersion.ps1 for version-compare context. Empty string for Dev.
solution_type"Unmanaged" for Dev (makers can edit). "Managed" for all other environments.
enable_backupWhen true, exports the current solution from the environment as a backup ZIP before importing. Recommended for UAT, FRS, Prod.
enable_blocking_checkWhen true, runs Invoke-BlockingCheck.ps1 to detect active flows or ownership locks. Fails the deployment if blockers found.
enable_version_compareWhen true, runs Compare-SolutionVersion.ps1. If installed version ≥ artifact version, sets skip_import=true — import, backup, and publish are all bypassed.
import_config_dataWhen true, runs pac data import after solution import using config-data/{name}-data.zip. Enabled for Prod only by default.
⚙️ Common inputs (apply to all envs) workflow_dispatch
mock_deployDry run. No Dataverse imports, no JFrog uploads. Also skips Stage 1 export automatically.
trigger_upgradeUse stage-and-upgrade (holding solution) pattern: imports as holding then calls pac solution upgrade.
base_solutionsComma-separated solution names to verify are installed in the target environment before import begins.
checker_error_levelMinimum severity that fails Solution Checker. Options: CriticalIssue, HighIssue (default), MediumIssue, LowIssue, InformationalIssue.
solutions"all" or comma-separated solution names. "all" resolves all solutions from solutions.json, sorted by deployOrder.
skip_exportSkips Stage 1 — builds from committed src/solutions/ instead of exporting from sandbox. Useful for config-only or hotfix runs.

Solution Ordering — solutions.json

📋 deployOrder field solutions.json
deployOrderInteger. Controls sequential deploy order within each environment — lowest number imports first. No dependency enforcement — purely positional ordering.
dependsOnArray. Documentation metadata only — records logical prerequisites but has NO effect on deploy order. Use deployOrder for sequencing.
Example: CoreSolution(deployOrder:1) → ExtensionA(deployOrder:2) → ExtensionB(deployOrder:3)
