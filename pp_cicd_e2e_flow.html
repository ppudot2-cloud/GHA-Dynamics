Multi-solution: All workflows accept a solutions input — "all" deploys every solution in src/solutions/; comma-separated names deploy a subset. Dependency order controlled by .github/solutions-config.json.  |  Two-repo split: deploy-dev.yml and rollback.yml in GHA-Dynamics are thin wrappers. They read vars.* (inaccessible in reusable workflows) and delegate all logic to GHA-Core.  |  Artifact flow: Build → GHA artifact upload (solution-{name}-{run#}) → Deploy downloads from GHA. JFrog receives uploads in build and gets tagged after Prod — but is NOT the download source.  |  Solution backup: export-solution@v1 (not backup-environment@v1). Artifact: backup-{solution}-{env}-v{run#}. Rollback re-imports this ZIP via import-solution@v1.  |  Blocking check: Warn-only — pipeline never fails from async ops count. OAuth failure still fails fast (credential error).  |  Job summaries: Each build and deploy job uploads a JSON artifact. pipeline-summary job downloads all with pattern job-summary-* and renders consolidated report.  |  Gate pattern: Lightweight gate job with environment: (no matrix) before each deploy matrix — ONE approval covers all N solutions.

🔀 How Variables & Artifacts Flow Through the Pipeline

vars.* boundary handling:
GHA-Dynamics wrapper reads:
  vars.PP_DEV_URL
  vars.PP_INTG_URL ... etc

Forwards as string inputs:
  with:
    pp-dev-url: ${{ vars.PP_DEV_URL }}
    pp-intg-url: ${{ vars.PP_INTG_URL }}

GHA-Core reusable receives:
  inputs.pp-dev-url (string)
  inputs.pp-intg-url (string)
Build → Deploy artifact flow:
Build job:
  upload-artifact@v4
    name: solution-{name}-{run#}
  JFrog upload (traceability)

Deploy job (unconditional):
  download-artifact@v4
    name: solution-{name}-{run#}
